# AI 智能体技能包：外部资源核查与治理机制适配

> **缘起**：收到一个面向 AI 智能体的技能包站点 `maker-skills.com`（对应开源仓库 `coreyhaines31/makerskills`），请教"有哪些可用内容可以纳入本库"。
> **本文做三件事**：① 对包内 **21 个技能逐一判定**（✅ 已有 / ➕ 增量 / ❌ 不可用）；② 对它有、本库没有的 **4 套元方法**做适配论证（本文最高价值段）；③ 给出**明确的不纳入清单与理由**，并列出与本机既有技能的对账结论。
> **一句话**：**这个包与创客空间的领域知识 0 重叠**——它的 21 个技能没有一个谈空间、设备、教育或运营；但它有 **4 套治理与判断层的元方法**，恰好命中本库当前最实的两块空白（**文档的信任状态与取代关系**、**"改不了"之前的破墙程序**）。

## 二、核查口径

三条判据，缺一即降档（与 [空间动线与摆放规划-外部知识包核查](空间动线与摆放规划-外部知识包核查与开源工具适配.md) §二 同口径，便于横向比较）：

| 判定 | 含义 | 处置 |
|---|---|---|
| ✅ 已有 | 本库有等价或更强的机制 | 引用即可，不新建 |
| ➕ 增量 | 本库确无，且能直接用于本项目 | 列入补充候选 |
| ❌ 不可用 | 与项目范围界定冲突 / 语境不匹配 / 无依据 | 记入本文并写明理由 |

> ★ **一条前置纪律**：本库对"通用方法论"的收录门槛是**它必须能回答本项目的一个具体判断**。该包多数技能属于"个人经营者的通用效能工具"，与本库"规划 / 建设 / 管理"三环节不相交，因此按 **❌** 处理；只有能改写成本库一条可执行纪律的，才升为 ➕。

## 四、★ 机制一：文档的"信任分级"与"弃用代替删除"

> 来源：`company-brain`。这是本包**最有价值、也最贴合本库当前痛点**的一套机制。

### 4.1 它解决的问题

多人 / 长期维护的知识库里，"信息错了"和"信息旧了"是两种不同的病，但常见处理都是**直接改掉**——历史与判断依据一起消失。`company-brain` 的解法是加一个**四值枚举**字段（有意用枚举而非 0–1 权重，理由是"团队能维护四个值，没人维护一个浮点"）：

| trust 值 | 含义 | 查询时怎么对待 |
|---|---|---|
| `unreviewed` | 抓进来了，但没人确认过（**每个新条目的默认值**） | 可用，但显式标降置信（"这条大部分依据未复核"） |
| `verified` | 有人看过并确认是对的 | 全权重 |
| `deprecated` | 错的或过时的，只为留档 | **绝不作为上下文**，最多作指针 |
| `superseded` | 被更新的东西取代，附 `superseded_by` 指针 | 绝不作为上下文，查询直接指向替代者 |

★ 三条关键设计：

1. **弃用代替删除**——"原始条目永不删除"这条铁律保持不变，但错 / 旧信息被标 `deprecated` 后自动退出上下文。**历史保留，上下文受保护。**
2. **trust 与业务状态字段分开命名**——它明确避让：业务生命周期用 `status`（潜在 / 成交、已决 / 已推翻），信任用 `trust`，两者不得混用一个字段。
3. **有一套对应的"剔除工序"**——`/cb review` 逐条走队列，四个处置（verify / deprecate / supersede / skip），除 skip 外都盖 `reviewed` + `reviewed_by` 戳；一次剔除产出一份带审计痕迹的 `outputs/<日期>-review.md`。**下游联动**：被弃用的条目如果喂过 wiki 页，那些页会被列出来要求重编译。

另有**敏感度分层**（`internal` / `leadership` / `confidential`）：查询模式先认调用者身份，拒绝纳入高于其级别的条目；wiki 页**继承其来源中的最高敏感度**。

### 4.2 与本库对账

| 能力 | 本库现状 | 判定 |
|---|---|---|
| 复核周期 | [CONTRIBUTING](../CONTRIBUTING.md) §五：时效敏感 6 个月 / 方法论 24 个月；`_kbcheck.py --review-due` 可列到期文档 | ✅ 已有 |
| 反面案例留档 | [口径事故与返工记录](../00-知识库治理/口径事故与返工记录.md) A-01…A-18，统一五段式 | ✅ 已有（**手工版的 deprecated 记录**） |
| 取代关系 | 部分文档有"已被本库文档替代"的正文表述，**没有统一登记** | ➕ 缺口 |
| 单篇信任状态 | **无**。现在判断一篇文档"是否已过复核"只能读 frontmatter 的 `date` 猜 | ➕ 缺口 |
| 敏感度分层 | 公开库 + 项目私有仓**物理分离**（A-11 ⑤），比字段分层更安全 | ✅ 已有且更强 |
| 剔除审计痕迹 | §6.1 更新日志 = 手写的剔除记录 | ✅ 已有 |

### 4.3 落地建议（**分两个库分别处理，不要一刀切**）

- **本库（公开知识库）**：**不引入 `trust` frontmatter 字段**。理由：会破坏六字段规范、需要重扫 122 篇、且公开库的"未被复核"语义已经由 `date` + §6.3 复核周期表达。
  - ✔️ 采纳的只有两点：① **弃用代替删除**——文档作废时不删文件、不掏空正文，改为在正文顶部加"已被取代，见 XXX"横幅（本库归档横幅已有先例）；② **取代登记表**——在治理文档增设一张"一篇一行的取代映射表"，让"谁替代了谁"可被脚本读取。
- **项目私有仓 / 团队协作场景**：`trust` 四值 + `sensitivity` 分层 + `review_by` / `last_reviewed` + `review_cadence` 是**开箱可用的完整模型**，建议整组采纳。它与本项目"客户信息不得进公开仓"的既有边界互补——**边界管"能不能出去"，trust 管"进来之后可不可信"，敏感度管"谁能看"**。

## 五、★ 机制二：破墙框架——把"改不了"从结论改成程序

> 来源：`unstuck`。**直接命中本项目的一个真实痛点**：范围界定硬规则要求"每条能改写成『要求甲方做到 X』，改不了就是越界"——但**"改不了"本身从未被程序化检验过**。

### 5.1 核心命题

> **"不可能"是一个主张，不是事实。** 它几乎总能解压成更弱的东西：*贵*、*违规*、*没人做过*、*我不知道怎么做*。只有**真正不可能**（物理、数学、算术）才该结束会话——而且它诚实结束。

### 5.2 墙的六分类（**类型决定撬棍**）

| 墙型 | "不可能"实际意味着 | 主导技法 |
|---|---|---|
| 假设型 | 一个继承来的、没人再验证过的信念 | T1 假设尸检、T3 第一性原理 |
| 框架型 | 目标被表述成"把答案排除在外"的样子 | T4 高度切换、T2 反演、T5 从终点倒推 |
| 守门型 | 某人 / 某机构说了不 | T10 审问那个"不"、T6 类比迁移 |
| 工具型 | "X 不支持 Y" | T9 SCAMPER、T6 类比迁移 |
| 资源型 | 时间 / 钱 / 人不够 | T7 约束双向翻转、T8 挑衅式乱入 |
| 物理数学型 | 真不可能（**罕见**） | 诚实退出：改道目标，这堵墙是承重的 |

### 5.3 三条可直接搬进本库纪律的规则

1. **★ 假设尸检永远先跑**：把问题陈述逐字写下 → 列出其中**每一个假设，含隐形假设**（选用的名词、预设的动作主体、暗示的顺序、假定的工具）→ 每条标 **"已验证事实"（你自己近期查过）** 还是 **"继承信念"（文档说的 / 某人说的 / 一直这样 / 我以为）** → 便宜的立刻测。
   > ★ 对照本项目：**"位置穷举已证是算尽后的结论"正是这条的产物**——但当时没有把它固化成纪律，下一次还会有人（或 AI）重启同一轮穷举。
2. **★ 报死路必须先附"已试角度清单"**。"若最终仍要向用户报告死路，10 角度门槛照样适用——**死路报告正是这门槛存在的时刻**"。绝不允许裸的"这个不支持"。
   > ★ 对照本项目：这正是"不在没跑过自检的情况下说已入库"的同构纪律，只是**对象从文档换成了判断**。
3. **★ 承重墙退出是成功，不是失败**。"在真实尝试之后宣布一堵墙承重，是一次胜利——它把弥漫的挫败感转换成一个清晰的改道"。

### 5.4 附带的执行纪律（可直接抄）

- **先做两高度重述**：一句更抽象（这一步在服务什么工作？能不能不做这步就完成那个工作？）、一句更具体（到底哪一行、哪个字段、第几步失败？）——**很多墙只在某一个高度上存在，换高度就溶解了**。
- **数量门槛按"种类"计**：生成阶段不评估、不说"但是"；10 个角度里若有 3 个是"再问一次但态度好点"，那算 **1 个**角度。
- **"我什么都试过了"要清单**——"什么都试过"通常实际只有 2–3 件事，**"什么都"与真实清单之间的差距，通常正是答案所在**。
- **时间盒 20–40 分钟**，"这是撬棍，不是哲学研讨班"。
- 四条反模式：**化装角度**（把 3 个想法改写成 10 个）、**过早可行性判断**（生成期说"那不行"会杀掉那颗能长出可行方案的种子）、**技法旅游**（10 个技法都浅跑一遍不如 3 个跑透）、**跳过重述**（对表述错误的问题用技法，只会得到"组织良好的错误答案"）。

## 六、★ 机制三：决策日志——做决定这件事本身就是记录它的动作

> 来源：`decide`。**本项目的决策密度极高**（9 条红线、X 一票否决、三条代价三选一、v2.9 §十四定夺项、设备清单 Q1–Q12），但**没有一处记录"为什么这么定"并约定回头看**。

### 6.1 五问永远问 + 按特征加题

| 角色 | 问题 |
|---|---|
| 默认 5 问 | ① 这个决定**真的需要做**吗 ② 做决定的**是正确的人**吗 ③ 有多容易**反悔** ④ **第一直觉是什么** ⑤ **一年后**回看会怎么想 |
| 不可逆 / 单向门 | 加上：有没有一个"错"的选项 / 连锁影响 / 会弯折哪条原则 |
| 有时间压力 | 为什么在犹豫 / 明天来判断会不同吗 / **什么时候必须定** |
| 涉及多人 | 在做别人的功课吗 / 再来一个意见有用吗 / 是否多人合议了一件该一人定的事 |
| 数据很多 | **什么缺失信息会改变结论** / 数据还是直觉 |
| 会重复发生 | 上次怎么定的 / 是一次性还是反复 |
| 对外 | 外面有人在等吗 / 影响偏客户还是偏我们 |
| 花钱 | 本质是钱的问题吗 / 投入产出 / **说了"行"会挤掉什么** |
| 大块时间 / 精力投入 | 机会成本 / 产出的投入回报 / 是在创造工作还是在消灭工作 |
| 卡住不定 | 为什么还没定 / **不决定会怎样** / 你到底在不在乎 |

★ **上限约 8 题**——"超过就变成分析瘫痪，而分析瘫痪正是这套流程要防的东西"。

### 6.2 三条最锋利的规则

1. **★ 第一直觉是神圣的：必须在分析之前捕获。** "如果最终结论与第一直觉不一致，理由部分**必须解释为什么**——这正是这一问存在的全部意义。"（否则所谓分析只是合理化。）
2. **★ 结论必须明确，五选一**：现在定 / **拆小再定**（拆成 2–3 个更小的决定）/ 等（并写清等什么）/ 不定（这事不需要决定）/ **找对人定**。
3. **★ 复查日期按"后果显现的时间"定**，且必须写清"看什么"：工具 / 流程类 30 天｜战略 / 定位类 90 天｜合作 / 用人类 90–180 天｜上线类 30–60 天。复查项要写成可观察的事实（"流水动了吗""合作方发货了吗""客户还在问吗"），**不是只写一个日期**。

> ★ 归档格式（可原样搬进本项目决策日志）：`# 决定：<一行>` / 日期 / **决策期限** / **可逆性** / **赌注大小** / 背景 / 逐问答案（标题写问题原文，不写 Q3）/ **决定** / 理由 / **预期结果（到什么日期应看到什么为真）** / 复查（日期 + 看什么）/ 来源。

### 6.3 本项目适配

- 现有 `MEMORY.md` 的"待定夺"是**一张清单**，缺三样：**决定时的候选与理由**、**复查日期**、**事后对账**（当时判断对不对）。
- **最该先落的一处**：**AB 区三条代价三选一**（P-0）。它天然符合这套格式——可逆性明确、有可观察的后果、且当前正卡在决策点上。三个选项按这套格式各写一段，**"一年后怎么看"与"说了行会挤掉什么"这两问很可能直接改变排序**。
- 另一处高价值映射：本项目已有"决策要记理由"的**局部实践**（口径事故记录的"权威口径"段就是这个结构），把它从**事故场景**推广到**日常决策场景**即可，不需要新机制。

## 七、★ 机制四：外部资源移植的许可门与升级路径

> 来源：`skillify` 的 ADAPT 模式。**与本库 `06-资源索引` 正在做的大量"外部资源评估"直接相关**：本库已收录 30+ 个外部仓库，但**没有一套统一的移植登记规范**。

### 7.1 三桶分类（**先出表给人批，不得静默重写**）

| 桶 | 装什么 | 例子 |
|---|---|---|
| **原样保留** | 格式、schema、机制、脚本、框架 | 问题清单、命令行参数、正则、JSON schema |
| **适配** | 工具默认值、路径、命名、观点、语气 | 它的视频工具 → 本库的通道、它的看板 → 本库的流程 |
| **新增** | 交叉引用、组合说明、本库惯例 | "与 XX 文档组成一对""入链自 XX" |

★ **必须先把分类表交人确认再动手**——"不要静默重写，把改动摆出来"。

### 7.2 许可门（四级，可直接并列进本库既有许可纪律表）

| 许可 | 动作 |
|---|---|
| MIT / Apache-2.0 / BSD / ISC / CC0 | ✅ 绿——可继续 |
| MPL-2.0 / LGPL | 🟡 黄——可适配，但要提示文件级互惠 |
| GPL-2.0 / GPL-3.0 / AGPL | ❌ 红——传染风险，动手前必须显式呈报 |
| 专有 / 无许可 | ❌ 红——**停**。没有复制的法律依据 |
| 不明确 | 🟡 黄——先问；不确定就默认跳过 |

> 本库既有许可纪律表（见[空间动线与摆放规划-外部知识包核查](空间动线与摆放规划-外部知识包核查与开源工具适配.md) §6.4）已覆盖"可做什么 / 不可做什么"，**此处补的是"进门时的那道闸"+"移植后怎么追踪上游变化"**，两者互补不重复。

### 7.3 ★ 移植登记文件（本库当前没有，建议设一个模板）

七要素：**源 URL** ／ **仓库** ／ **作者** ／ **移植时的 commit SHA** ／ **许可（名称 + URL）** ／ **移植日期** ／ **三类改动（原样保留 / 适配 / 新增 各列清单）**。许可为 MIT / BSD / Apache 时，上游 LICENSE 文本一并附上。

★ **升级路径**（这是最容易漏的一条、也最省事的一条）：记下移植时的 SHA，日后用 `git ls-remote <repo-url> HEAD` 比对；**SHA 变了就重跑一遍做三方合并**。有这条，外部资源才不会"移植完就与上游脱钩、永远停在旧版"。

### 7.4 两条可迁移的"反浪费"纪律

1. **memory 与 skill 的分流**：一条学习如果是**某个技能专属的规则**→ 直接改那个技能；如果是**跨领域原则**→ 写成记忆条目；两者都是 → 两边都写。★ 本库对应：**内容类修订写入对应文档，元规则类写入 `00-知识库治理/`**——这条分流本库已在做，但**没有写成明文规则**。
2. **不要给外科手术式编辑加仪式**：加一行字就直接改。完整流程只在四种情况才值：① 一条学习影响**多个对象** ② 从长会话里**批量提取** ③ "改文档还是改治理规则"分不清 ④ 版本纪律要紧（正要提交、想要一个干净的版本语义）。★ 本库对应：这正是本库 `_hooks/pre-commit` 与"三处登记"之间应有的松紧关系——**登记要严，改一行字不必开 PR**。

## 十、落地建议

1. **P0 · 采纳"弃用代替删除"** —— 改 [CONTRIBUTING](../CONTRIBUTING.md) §五 / 治理文档：文档作废时**不删文件、不掏空正文**，在顶部加"已被取代，见 XXX"横幅；并在治理文档增设**取代登记表**（一行一条：被取代文档 → 取代者 → 日期）。
   **不要做什么**：不要给 122 篇文档批量加 `trust` 字段，也不要在体检脚本里加信任状态校验。
2. **P0 · 把破墙程序写成纪律条文** —— 在范围界定硬规则旁补一条：**判定"改不了 / 越界"之前，必须先跑一遍墙分类与假设尸检；任何"只能这样"的结论须附已排除的角度清单**。这条直接对应本项目"位置穷举"的既有经验。
   **不要做什么**：不要把 10 技法全表搬进本库（技法属通用工具书内容，本库收录门槛是"能回答本项目一个具体判断"）；只留**墙的六分类 + 三条硬规则 + 四条反模式**。
3. **P1 · 建一个决策日志**（项目侧，不进公开库）—— 先拿"AB 区三条代价"做第一例，走完"三问 + 复查日期 + 预期结果"。格式照 §6.2 归档模板。
   **不要做什么**：不要把所有历史决定补录一遍（补录的记忆必然失真）；只从**下一个尚未决的决定**开始记。
4. **P1 · 设一个外部资源移植登记模板** —— 落到 `06-资源索引/`，七要素 + 升级路径命令；许可门四级并入本库既有许可纪律表。
   **不要做什么**：不要为此新建一门大规范文档；它应是一张**可复制的表**，不是一章制度。
5. **P2 · 方案评审引入"指定反方"** —— 在多人评审场景（如方案 4′ 评审）固定安排一人持异见，并在综合结论前先列分歧点。
   **不要做什么**：不要引入"模拟名人顾问团"形态。
6. **P2 · 复核链路的幂等与退出条件** —— 借 `loopify` 的两个词：`_kbcheck.py --review-due` 的输出应**幂等**（同一天多次运行结果一致）、且**有显式退出条件**（复核完成后该文档从待办队列消失）。
   **不要做什么**：不要引入它的调度框架，本库的复核周期已由 §6.3 约定。
