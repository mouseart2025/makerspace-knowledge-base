# 口径事故与返工记录

> **本文档是什么**：知识库的「反面案例栏目」——只登记**做错了、返工了、差点出事**的实例，不登记成功经验。每条按统一五段式记录：错误口径 → 权威口径 → 如何发现 → 影响面与代价 → 防再发机制。
> **为什么需要它**：正面方法论（见 [AI空间方案工作流-九阶段端到端方法论](../02-空间搭建/AI空间方案工作流-九阶段端到端方法论.md)）告诉你"该怎么做"，但人只在**具体的错**上长记性。把错误实例、真实代价与拦截手段固定下来，下一次才可能少踩。
> **脱敏声明**：全部条目来自真实项目，已做不可逆脱敏——不出现委托方名称、不出现本地绝对路径、不出现可定位的图纸编号；项目统一表述为「某高职院校创客空间二期项目（L 型厂房改造）」。**坐标、数量、版本号、字高等技术细节保留**，因为它们是教训可复现、可验证的部分。
> **维护约定**：**追加式登记，不删旧条目**。新条目插在 §三 对应分类的**最前面**（倒序，最新在上），同时在 §二 索引表加一行、在 [知识库覆盖度分析与补充路线图](知识库覆盖度分析与补充路线图.md) §6.1 更新日志登记。条目编号 `A-xx` 一经分配不再复用；防再发机制后来升级的，在原条目内追加「⚠️ 机制已升级，见 A-yy」，不改写原文。

## 三、条目明细

### 口径类

#### A-01 🟡 门类编号与方位标签南北对调

- **错误口径**：平面图中「门1 / 门2」的方位标签与实际南北位置对调。坐标数据是对的，错的是**名称标签的挂载关系**；由此文档里「门2 供重型设备进出」这句话，实际具备该条件的是门1。
- **权威口径**：以**坐标**为唯一锚点。门洞坐标从 DWG/DXF 矢量文字层抽取，名称标签必须与坐标一一绑定后写入构件权威表；任何文档引用门号时，括号内同时给出坐标。
- **如何发现**：编制现场勘测任务说明书时做「门号 ↔ 坐标 ↔ 功能描述」三向对账，发现功能描述与坐标不匹配。
- **影响面与代价**：牵连设备进出路线、疏散方向、动线起点三处结论。若在对外报告发出后才暴露，需要整章重写并重新对齐三套方案。实际代价：说明书与 4 份分析文档的门口径统一重跑，约 3 小时。
- **防再发**：① 构件权威表（门/窗/柱/洞口逐条登记：编号 + 坐标 + 净宽 + 功能），作为一切下游文档的唯一取数处；② **三件套记录纪律**——每条实测数据必须同时留下「数值、照片、来源图元」，三者缺一即视为未测；③ 引用编号时附坐标，使错误可被读者独立复核。

#### A-02 🔴 关键决策项未闭环就出对外报告

- **错误口径**：主入口位置按「假定门4 / 门5」写入三套布局方案的对外体检报告，而项目既有记载是「门1 / 门2」；两种口径都未经委托方确认，报告却已按单一口径给出结论与排序。
- **权威口径**：主入口属**决策阻断项**，必须由委托方在现场确认后写入《需求规格书》。确认之前，所有依赖它的结论只能标注为「待确认口径下」，并显式给出双口径的数值差。
- **如何发现**：用同一份布局 QA 脚本对 4 种门口径各跑一遍（共 12 组实跑），发现严重项数量由 **7 变为 10**，差值足以改变方案排序与结论落点。
- **影响面与代价**：3 份对外体检报告 + 1 份选型建议全部需要加状态标注、降级为「实验性输出」；正式交付顺序重排为「现场勘察报告 → 需求规格书 → 正式布局报告」。代价：4 份文档补横幅与待校正口径表，交付节点后移。
- **防再发**：① **决策阻断项清单**——凡结论对某个未经确认的输入敏感，该输入即列为阻断项，未闭环不得出对外文档；② 出对外文档前必须做**多口径实跑**（用脚本跑，不靠估算），把差值原样写进文档；③ 对外文档一律带「状态标注 + 待校正口径表」，让读者第一眼看到哪些结论依赖未确认前提。

#### A-03 🟡 把校园总平面当成楼层平面底图

- **错误口径**：图纸包中一份文件名标注为「平面图」的 PDF 被当作一层平面底图使用，实际它是**校园总平面**——只有建筑轮廓、道路与场地关系，没有房间、门窗与轴网。
- **权威口径**：底图必须回源到 DWG/DXF 矢量文件，按图幅块渲染出目标楼层平面；使用前在图签处核对「图名 + 楼层 + 比例 + 出图日期」四要素，四项齐全才可作为底图。
- **如何发现**：抽取门窗表时发现该 PDF 内无门窗图元、无轴网编号，只有场地标注文字。
- **影响面与代价**：基于该底图的一轮矢量化与分区尝试整体作废，改用 DWG 管线重做，约半天。
- **防再发**：① 底图入库前先跑四要素核对，缺一项即退回；② **文件名不可作为图种判据**——「平面图」既可能指总平面也可能指楼层平面，必须看图签与图元；③ 管线与坑位详见 [建筑图纸矢量渲染与门窗表抽取工作流](../02-空间搭建/建筑图纸矢量渲染与门窗表抽取工作流-v1.md)。

### 版本类

#### A-04 🟡 版本标签错挂：文档标 v18、指标取 v19、模型只到 v18

- **错误口径**：方案文档标注「设备落位 v18」，但文中指标（通道净宽、严重项计数等）实际取自 v19 的数据脚本；同时 3D 模型只生成到 v18，插图与数值并不同源。
- **权威口径**：**指标、模型、插图三者必须同版**。若模型停在 vN 而指标取 vN+1，文档必须显式声明「指标基于 vN+1 数据脚本，几何模型为 vN，两者差异项如下」，不得默认读者知道。
- **如何发现**：编制权威版本索引时，把「文档声明版本 / 指标来源脚本 / 模型文件最高版」三列并排比对，错位一眼可见。
- **影响面与代价**：对外报告中的插图与数值不严格对应，需在文档内补版本对应表说明；若被委托方发现，会直接质疑全部数值的可信度。
- **防再发**：① **版本三元组登记**（文档声明版 / 数据脚本版 / 模型版）随方案文档一起维护；② 交付前跑一次三元组一致性检查；③ 禁止「指标先行、模型后补」而不声明。

#### A-05 🟡 13 组文件多版本并存，无权威版索引

- **错误口径**：同一文档存在 3 版以上并存（最多的一组有 9 版），没有任何一处说明「现在以哪版为准」，而旧版仍在被其他文档链接引用。
- **权威口径**：每个文件族必须有唯一权威版。判定依据 = 最高版本号 / 最新修改时间 / 被引次数，三者交叉验证；三者分歧时人工裁定，并把裁定理由写进索引。
- **如何发现**：全目录实扫，按「去掉版本号与后缀的文件名」归族，扫出 13 组 ≥3 版并存，其中 3 组三项判据互相分歧（例如权威版是 v18，但旧文档仍引 v15，而指标其实取自 v19 脚本）。
- **影响面与代价**：AI 检索与人工查阅都可能取到旧版，导致同一问题得到不同答案。代价：建立一份权威版本索引（实扫 45 篇 md、约 37 万字）并回改引用。
- **防再发**：① 维护**权威版本索引**（文件族 → 权威版 → 判定依据 → 分歧说明）；② **版本卫生 5 条**：新版发布即在同族旧版顶部加「已被 vN 取代」；引用一律指向权威版；文件名版本与内容版本必须同步递增；无版本号的工作稿不得与正式稿混放同目录；每季度重扫一次归族。

#### A-06 🟢 文件名复合后缀切断自动归族

- **错误口径**：正式文档命名中混入受众后缀（如 `…-v9-甲方版.md`），导致按「文件名去版本号归族」的脚本把它判成一个新族，与同族 v1–v8 断开。
- **权威口径**：受众与密级信息写在**文档内**（frontmatter 字段或正文状态标注条），不写进文件名；文件名只保留「主题 + 版本号」。
- **如何发现**：归族结果里该族只有 1 个成员，而人工判断它显然有 9 版。
- **影响面与代价**：低——不影响内容正确性，但会让权威版判定失真，进而放大 A-05 的风险。
- **防再发**：① 命名规范：`主题-vN.md`，受众写 frontmatter；② 归族脚本增加后缀剥离规则，并维护已知受众后缀白名单（甲方版/内部版/评审版等）。

### 工具类

#### A-07 🔴 脚本无参数 `save`，就地覆盖模型成果

- **错误口径**：批量改窗的 SketchUp Ruby 脚本使用 `Sketchup.active_model.save`（不带参数），直接覆盖**当前打开的模型文件**。一次跑错，上一版几何就被就地冲掉。
- **权威口径**：脚本保存必须写**显式目标路径**（`save("<新版本文件路径>")`），且改动前对当前模型做带时间戳的备份。无参数 `save` 属破坏性操作，禁止出现在批量脚本中。
- **如何发现**：跑完发现模型被就地覆盖、无法回退，只能从更早的脚本重新生成整段几何。
- **影响面与代价**：一次几何成果损失 + 重跑时间；排查后发现同类风险存在于整个自动化脚本族，需要逐支检视保存语句。
- **防再发**：① 脚本模板固定三段式：**改前备份 → 显式路径保存 → 保存后回读校验**（回读文件大小/实体数，确认写成功）；② 批量脚本一律先在副本上试跑；③ 工具类坑位集中登记在 [SketchUp 自动化与 AI 设备自动摆放：工作方法与踩坑记录](../06-资源索引/SketchUp自动化与AI设备自动摆放-工作方法与踩坑记录.md)。

#### A-08 🟡 150 dpi 栅格 PDF：屏幕清楚，打印不可读

- **错误口径**：把图纸按 150 dpi 栅格化输出 PDF，屏幕上看着清楚，A3 打印出来标注文字糊成一片，无法在现场手写记录。
- **权威口径**：现场用图必须是**矢量文字层** PDF。纸面可读下限 = 字高 ≥ 2 mm ≈ 5.7 pt（A3、正常光线、需手写标注的场景）；分幅缩放系数 s 必须满足「源文件中位字高 × s ≥ 5.7 pt」。
- **如何发现**：实打样张比对——栅格版放大后只有模糊像素，笔尖落不下去。
- **影响面与代价**：一整套现场打印包作废重做。若未在出发前发现，现场勘察将无法在图上落笔记录，等于白跑一趟。
- **防再发**：① 把「一切以矢量文字层为准，禁止栅格化放大凑数」写成管线第一原则；② 出图前统计源 PDF 的 `span size` 中位数做可读性断言，不达标不出图；③ 完整管线与五个必踩坑见 [建筑图纸矢量渲染与门窗表抽取工作流](../02-空间搭建/建筑图纸矢量渲染与门窗表抽取工作流-v1.md)。

#### A-09 🟢 Markdown 表格列数缺陷，随复制潜伏数版

- **错误口径**：一份对外报告中的疏散距离表，表头 5 列、数据行只有 4 列，渲染后整列错位；该缺陷随文档复制传播到多个版本，潜伏数版无人发现。
- **权威口径**：所有 markdown 表格必须满足「表头列数 = 分隔行列数 = 每个数据行列数」。
- **如何发现**：写了一个全库表格列数一致性扫描脚本，一次扫出该处（其余 44 篇 0 问题）。
- **影响面与代价**：低——修复只补齐缺失的「判定」列，内容零改动。但**它是对外报告**：若未被扫出，委托方看到的就是一张错位的判定表，直接损伤专业可信度。
- **防再发**：① 表格列数校验并入体检脚本与提交前检查；② 对外文档发布前跑**全库**扫描，不只扫本次改动文件——缺陷常常潜伏在未被触碰的旧文件里。

  > ✅ **机制已升级，见 A-13**：本条 ① 当时只是"并入"的意向，实际由一次性脚本代行、未进常驻体检；2026-09-14 才真正实现为 `_kbcheck.py` 第 9 类检查，并入后立刻在另一篇**已发布**文档中查出 4 处同类缺陷。

### 流程类

#### A-17 🟡 规范写了受控词表，校验却只查字段在不在：`type` 静默长出 13 类、`scope` 2 处越界

- **错误口径**：`CONTRIBUTING.md` §2.1 给出 `type` 的 7 类取值，但 `_kbcheck.py` 第 6 类 frontmatter 检查只验证六个字段**是否存在**、不验证 `type` / `scope` 的**取值**。于是「受控词表」只是文档里的一段倡议，没有任何机器可判定性——字段里写什么，都算合格。
- **权威口径**：凡在规范中列为「受控词表」的字段，其取值集合必须与校验脚本**同源**：词表定义为脚本常量（`TYPE_VOCAB` / `SCOPE_VOCAB`），取值越界即 ERROR；规范文档与脚本常量的改动必须在**同一次提交**内完成，禁止只改一边。
- **如何发现**：2026-09-20 全库盘点，按 `type` 取值分组统计，实际出现 **13 类**，远超规范声称的 7 类——`专题补充`（25 篇）、`专项方案`（13 篇）、`资源索引`（12 篇）等全部越界，且长期无人察觉、pre-commit 一路绿灯；`scope` 另有 2 处擅自取值（`科普场馆参考`、`空间搭建/现场勘察准备`）。**字段在不在能查，取值对不对没人查**——这与 A-15「覆盖面未声明就宣称已扫」同源：都是把「我以为查了」当成「已经查了」。
- **影响面与代价**：中——不影响单篇内容正确性，但**任何按 `type` / `scope` 做的筛选、统计、路由都建立在失真的集合上**；且词表失控随时间单调恶化（本次已积累到 13 类）。处置：① 归并 30 处取值到 9 类 `type` 受控词表与 2 类 `scope` 词表；② 脚本新增 ERROR 级 `type越界` / `scope越界` 检查；③ `CONTRIBUTING.md` §2.1 与治理文档规模口径同步。约 2 小时，无文档内容返工。
- **防再发**：① `TYPE_VOCAB`（入口/治理/方法论/规范/方案/案例/资源/索引/专题补充）与 `SCOPE_VOCAB`（通用/本项目专项）写入 `_kbcheck.py`，越界即 ERROR，并把 `type越界` / `scope越界` 前置到错误分组排序；② 新检查**上线即自证**（沿用 A-13 / A-15 纪律）：植入 `type: 随便乱写` 能被拦、还原后恢复全绿，正反两组均实跑；③ `CONTRIBUTING.md` §2.1 明示哪些字段是受控词表、全集是什么，并写入「**规范改动与脚本改动同提交**」纪律。
- **一句话**：**没有校验的规范等于没有规范——「受控词表」不进脚本，就只是文档里的一段美好愿望。**

#### A-16 🔴 脱敏词表只收委托方名的中文写法，罗马化（拼音）写法整批漏扫

- **错误口径**：本地词表 `_local_secrets.txt` 里，委托方名只登记了**中文写法**。`_kbcheck.py` 第 8 类检查据此只匹配中文串；而脚本、插件、日志里的标识符用的是**罗马化（拼音）**——插件注册文件名、Ruby 模块名、日志路径（形如 `<拼音>_autoload.rb` / `<拼音>AutoLayout`）全部不在匹配范围。**中文写法清干净 ≠ 脱敏完成**。

- **防再发**：① 词表按「**中文 + 罗马化成对收录**」维护，新增委托方时两种写法一起加，并在词表内写明该纪律；② 复查与公开前扫描**同时跑两组**（中文串 + 罗马化串），任一组有命中即视为未净；③ 本条目进护栏清单，与 A-11（内容）、A-14（身份）、A-15（载体覆盖面）并列，构成「脱敏四问：写法全不全 / 载体全不全 / 历史净不净 / 身份纯不纯」。

#### A-15 🟢 脱敏扫描覆盖面与 SOP 声称口径不符：只扫 .md/.py，根级合规文件整类漏扫

- **错误口径**：`_kbcheck.py` 第 8 类脱敏检查把覆盖面写死为 `SECRETS_SCAN_EXT = (".md", ".py")`，而《公开前安全核查与历史遗留对象处置规程》§三 1a 与 A-11 防再发 ② 都声称扫描对象是「**会被发布的文件集**」。两处口径不一致：`publishable_files()` 本已正确算出全量可发布集合（已跟踪 ∪ 未跟踪未忽略），却紧接着被扩展名过滤器砍掉一大半——`LICENSE` / `NOTICE` / `CITATION.cff` / `.sh` / `.json` / `.yml` / 无扩展名文件全部漏扫。脚本对此**不做任何声明**，于是使用者会把「0 命中」读成「全仓干净」。
- **权威口径**：第 8 类覆盖面 = 「会被发布的文件集」中的**全部文本载体**，只按二进制扩展名黑名单（图片/Office/PDF/CAD/音视频/字体/压缩包）与单文件体积上限排除；无法按 UTF-8 解码者自然跳过。**覆盖面数字必须与结果一同输出**（`--stats-md` 的「脱敏扫描覆盖面 / 命中」），否则「0 命中」不可判定——这正是 A-13 立的规矩。
- **如何发现**：为公开仓正式化新增 `NOTICE` / `CITATION.cff` 时，按 A-12 纪律重跑公开前核查、逐条对照 SOP §三 1a，发现脚本实际扫描集合与 SOP 声称集合不等。随后按 A-13 纪律做「上线即自证」：植入 5 个非 `.md` 载体（无扩展名 / `.cff` / `.sh` / `.json` / `.txt`）各含 1 个词表词——旧实现 **0 命中**，扩面后 **5/5 命中**，覆盖面计数同步由 105 → 110，证明计数器反映真实扫描集。
- **影响面与代价**：低——在**任何内容对外发布之前**发现并修复，未产生泄漏，无返工文档。但若不修，本次正式化新增的 `NOTICE`（版权声明与第三方授权说明，恰恰是最容易被手改的载体）将长期处于「声称已扫、实际未扫」状态，属 A-13 同类缺陷（覆盖面未声明）在合规维度的重演。代价：约 0.5 小时定位 + 补丁 + 双向自证（正例 5 用例、反例 4 用例）。
- **防再发**：① 覆盖面口径由**扩展名白名单**改为**二进制黑名单 + 体积上限**，新增文本载体自动纳入，不再需要改代码；② 覆盖面数字进 `stats` 与 `--stats-md`（沿用 A-13 纪律），"0 命中"从此必须附带"N 个文件已扫"；③ 自证过程中另查出**非 UTF-8 的 `.md` 会让脚本崩在读取阶段**（`UnicodeDecodeError` 未捕获，使用者只看到一串 traceback、无法定位是哪个文件），一并新增第 0 类「编码」检查与 `read_md_safe()`：跳过该文件内容并给出可读 ERROR，同时剥离 BOM 以免 frontmatter 被误判为"缺失"；④ 新增或改动检查项，上线前必须跑「应报 / 不应报」两组用例（A-13 已立，本条再次验证其必要性——反例组正是抓出崩溃缺陷的那一组）。

  > 📌 **同一口径的两种载体必须同步**：SOP 文档与体检脚本描述的是同一件事，任一处改了覆盖面，另一处必须同步；否则就会出现"文档承诺 A、工具实际做 B"的静默缺口。这类缺口不会报错，只会让下游决策建立在错误的安全感上（与 A-12「用无效证据判定风险已消除」同源）。

#### A-13 🟢 一次性脚本给出的"全库 0 问题"没有覆盖面，同类缺陷在已发布文档里继续潜伏

- **错误口径**：A-09 修复后写了一个**一次性**的表格列数扫描脚本，得出结论"扫出该处，其余 44 篇 0 问题"，随后脚本没有并入常驻体检工具，结论也**没有标明扫了多少文件、多少表格块**。"0 问题"被默认等同于"全库干净"。
- **权威口径**：任何"全库 0 问题"的结论都必须同时给出**覆盖面数字**（文件数 / 被检对象数），否则它只证明"我扫到的那些没问题"。一次性脚本要么并入常驻体检工具（`_kbcheck.py` + pre-commit hook），要么在结论里明确标注为"本次抽检 N 篇"。
- **如何发现**：2026-09-14 把表格列数校验并入 `_kbcheck.py` 第 9 类检查后首跑，在 **97 篇 / 675 个表格块**中报出 `02-空间搭建/设备摆放与布局规范.md` 两张表共 **4 个数据行缺「来源」单元格**（3 列表头对 2 列数据行）。
- **影响面与代价**：缺陷位于**已公开**的通用规范文档，渲染后整列错位，与 A-09 完全同类。潜伏期约一个月。修复代价约 20 分钟（并入检查 ~50 行 + 补 4 格 + 四处登记）。判 🟢 而非 🟡：属格式层面、不含错误信息、无下游数值或排序被改动。
- **防再发**：① 表格列数校验**并入常驻体检**——`_kbcheck.py` 第 9 类检查 `scan_tables()`，定级 ERROR，pre-commit hook 直接拦；② 实现上做两条纠偏：**转义竖线 `\|` 不计为列分隔符**、**代码围栏（``` / ~~~）内的行一律跳过**，否则正确表格会被误报——第一版正则把 `|` 误当成 alternation，一次误报 **675 处**，靠 3 个单元用例当场抓出（这条本身说明：新检查项上线前必须先跑"应报/不应报"两组用例）；③ `--stats-md` 增列「表格块 / 列数异常」两个数字，让**覆盖面本身可复核**；④ 补格沿用该文档既有惯例 `—`（表示无编号来源），不臆造出处；⑤ **上线即自证**：新检查项第一次全库跑，除了查出上述 4 处旧缺陷，还当场抓出**登记它自己的那一行 §6.1 日志**里有个未转义的裸竖线字符（写在行内代码里，肉眼几乎不可能发现）——说明该检查确实覆盖到了"新写的内容"，而不只是旧文档。

#### A-12 🔴 用无效证据判定风险已消除："private 下的匿名 404"被当成"缓存已清"

- **错误口径**：仓库转 private 后，用**未认证**请求访问旧 commit 页与 raw 直链，得到 404/403，据此判定"托管平台侧旧对象已清理，可择期恢复 public"，并把该结论写进交接文档当作"已处置"。
- **权威口径**：**private 状态下匿名访问任何东西都是 404**，这个结果不含任何关于对象是否存活的信息，不能作证。判定旧对象是否已被清理，必须用**具备仓库权限的认证 API** 直接查那个 SHA：`GET /repos/{owner}/{repo}/commits/{old_sha}` 与 `GET /repos/{owner}/{repo}/contents/{path}?ref={old_sha}`——返回 200 = 对象仍在（一旦公开即泄漏），404/422 = 已不可达。
- **如何发现**：执行"恢复 public"前重做一次**认证态**核查。结果与上一轮判断**双双相反**：① 被认为"仍被缓存"的那个旧 SHA 其实已 404；② 上一轮历史重写留下的**孤儿代 30 个提交全部存活**，其根提交下仍能取出脱敏前原文（真名命中 7 处、6,319 字节），且中间代提交的 tree 哈希与现历史某提交完全一致（说明第二代重写只改了提交元数据、未改内容）。
- **影响面与代价**：若按旧结论直接 `PATCH private=false`，脱敏前的委托方名称会**重新对全世界可读且不可撤销**（爬虫与网页存档会在分钟级抓走）。实际代价：公开动作被拦下，改为先清理对象库再翻转；同时纠正了一处"已处置"的虚假安全感——这类虚假安全感比未处置更危险，因为它会让人停止警惕。
- **防再发**：① **验证条件等价原则**——要证明"公开后不可读"，验证必须在公开状态或等价的**认证态对象查询**下做；用私有态的 404 作证等于没验证；② 公开前置检查固化为三步：本地 `git log --all -S"<词>"` 0 命中 → 认证 API 逐个查历史重写前的旧 SHA（孤儿代至少查**根/中/尖**三个提交）→ 全部 404 才可翻转可见性；③ 写结论时必须标明**证据获取时的仓库可见性状态**，否则读者无法判断证据是否有效；④ 高危不可逆动作（转 public、删仓、强推、覆盖保存）执行前**重跑一次核查**，不复用历史结论。

  > ✅ **机制已固化**：本条 ② 的三步核查已扩写为独立 SOP，含三层洁净模型、命令模板、结果判读表、三条处置路径与工单模板、12 项检查表，见 [公开前安全核查与历史遗留对象处置规程](公开前安全核查与历史遗留对象处置规程.md)。

#### A-10 🟢 新增文档入库未登记，等于没写

- **错误口径**：一批 4 篇新文档提交入库后，未在 README 结构导航树登记、未进 GLOSSARY 术语映射、也未写进治理文档更新日志。

- **防再发**：① `_kbcheck.py` 十类检查（**编码** / 断链 / 库外引用 / 孤岛 / README 登记 / GLOSSARY 登记 / frontmatter / date 粒度 / 脱敏 / 表格列数）+ README 树排版检查；② **pre-commit hook 强制拦截**——版本化副本在 `_hooks/pre-commit`，安装方式见 [README「提交前自检」](../README.md)；③ 治理文档 §6.3 已写入「新增文档后必须跑一次」。

#### A-11 🔴 真实委托方名称进入公开仓库 git 历史

- **错误口径**：知识库以公开仓库托管，但早期文档与脚本中写入了真实委托方名称与本地绝对路径。后来虽在**当前版**改为中性称谓，但**历史提交中的原文仍可通过旧 commit SHA 直接读取**，包括 raw 文件直链。
- **权威口径**：公开仓库中不得出现真实委托方名、本地绝对路径与个人隐私；项目专项内容统一表述为「某职业院校 / 某科普场馆」等中性称谓。已入库的敏感内容必须做**历史重写**，只改当前版无效。
- **如何发现**：开源前做词表驱动的全库脱敏扫描，并额外用 `git log --all -S"<敏感词>"` 检索**全部历史**，确认命中范围与提交数。
- **影响面与代价**：高——敏感内容曾在公开可读状态暴露一段时间。处置四步：① 用 `git filter-repo` 重写历史；② 仓库立即转 private；③ 向托管平台提交缓存清理请求（旧 commit 页面与 raw URL 的平台侧缓存不会因历史重写立即失效）；④ 确认 forks = 0 后，等缓存清理完成再恢复 public。
- **防再发**：① 本地脱敏词表 `_local_secrets.txt`（含真实委托方名与路径前缀，已被 `.gitignore` 排除，**绝不入库**）；② `_kbcheck.py` 第 8 类检查对「会被发布的文件集」（已跟踪 ∪ 未跟踪未忽略）中的**全部文本载体**做词表扫描，命中即 ERROR（覆盖面口径见 A-15，`--stats-md` 输出实际扫描文件数）；③ 诊断输出**只报词表序号、不报词本身**，避免报告被转贴时二次泄漏；④ 开源前必跑 `git log --all -S` 历史检索——**当前版干净不等于历史干净**；⑤ **公开仓与项目仓物理分离**：含委托方信息的项目工作目录单独建仓，且只能配 private 远端。

  > ⚠️ **机制已升级，见 A-12**：本条 ④ 的"历史检索"只覆盖**本地**历史；托管平台侧是否仍留有孤儿代对象，必须用认证 API 查旧 SHA 才能判定（`git log --all -S` 查不到远端对象库）。认证态核查的完整命令模板、结果判读与三条处置路径见 [公开前安全核查与历史遗留对象处置规程](公开前安全核查与历史遗留对象处置规程.md)。

#### A-14 🟡 提交被挂到陌生第三方账号名下（占位身份撞上真实账号）

- **错误口径**：自动化会话里临时用 `git -c user.name=… -c user.email=<某用户名>@users.noreply.github.com` 指定了一个"匿名占位身份"，以为只要邮箱是 `*@users.noreply.github.com` 就等于"不暴露真实信息"。实际 GitHub 上存在一个与该占位名同名的**真实账号**（2019 年注册），于是这 2 个提交在贡献者列表、`git log`、`/commit/<sha>.patch`、Atom feed 里都被归属给了**别人**，公开后会凭空多出一位"共同贡献者"。
- **权威口径**：本库提交身份**唯一且必须**等于仓库归属账号 `mouseart2025 <lei.feng@seeed.cc>`——该邮箱就是该 GitHub 账号自己的注册邮箱，属账号自身信息，**不算隐私泄漏**（账号主人已确认）。因此其余 34 个提交无需重写。禁止任何占位名、临时名，以及**由他人用户名派生**的 noreply 地址；确需匿名时只能用归属账号自己的现代 noreply 形式 `<账号ID>+<账号login>@users.noreply.github.com`。
- **如何发现**：账号主人在 GitHub 提交列表里看到署名与其余提交不一致而提问；随后 `git log --all --format='%an <%ae>' | sort | uniq -c` 复核，得 **34 : 2**。
- **影响面与代价**：中低——文件内容零变化（重建前后 HEAD 的 tree 哈希完全一致），无敏感信息外泄；但**作者归属错误只能靠重写历史修复，改当前版无效**，且若不处理就会随"恢复 public"一起对外发布。处置：`git commit-tree` 逐个重建顶部 2 个提交（保留 tree、提交信息、author/committer 双时间戳）→ `git update-ref` 原子替换分支指针 → 前 34 个提交 SHA 不变；项目专项 private 仓同步处理。
- **防再发**：① `_hooks/pre-commit` 增加**提交身份守门**：生效的 `user.name`/`user.email` 不在白名单内直接拒绝提交（绕过需显式 `KB_ALLOW_IDENTITY=1`）；② [公开前安全核查与历史遗留对象处置规程](公开前安全核查与历史遗留对象处置规程.md) §三 新增 **1d 提交身份一致性核查**（作者与提交者双维度去重，必须只有归属账号一种）并进 §九 检查表；③ 纪律：自动化会话**不再显式传 `-c user.*`**，一律沿用仓库/全局既有配置。

  > 📌 **提交元数据也是公开面**：A-11 管"文件内容"，本条管"提交对象自带的作者名 / 邮箱 / 时间戳"。二者都会随 `/commit/<sha>.patch`、`git clone`、feed 一起交出去，且都**只能靠重写历史修复**。公开前必须两步都查。

  > ⚠️ 核查口径的坑：历史重写后 `git log --all` 会把**尚未刷新的** `refs/remotes/origin/main` 旧提交也计入（本次表现为 38 ≠ 36）。身份一致性判定必须以**分支**为口径（`git log <branch>`），或在 `git fetch --prune` 之后再用 `--all`。

## 六、如何追加新条目

1. 在 §三 对应分类下**最前面**插入条目，套用下方五段式模板；编号顺延（不复用已删号）。
2. 在 §二 索引表加一行；若引入了新护栏，在 §四 汇总表加一行。
3. 在 [知识库覆盖度分析与补充路线图](知识库覆盖度分析与补充路线图.md) §6.1 更新日志登记日期与内容。
4. 跑 `python3 _kbcheck.py`，确保 0 ERROR / 0 WARN（脱敏检查会拦下真实委托方名与本地路径）。
5. 提交（pre-commit hook 会再跑一遍，不通过则拒绝提交）。

```markdown
#### A-xx 🔴/🟡/🟢 一句话标题

- **错误口径**：当时怎么写的 / 怎么做的。
- **权威口径**：正确的、可验证的表述是什么。
- **如何发现**：靠什么机制或什么偶然发现（能自动化发现的，写明脚本/检查项）。
- **影响面与代价**：牵连哪些结论与文档，返工花了多少时间，是否已流出到对外交付物。
- **防再发**：① …… ② …… ③ ……（每条都要落到具体载体：脚本、模板、清单或文档章节）
```

> **写条目的三条纪律**：① 不写"下次注意"这类无法验证的措施——防再发必须落到**载体**（脚本/模板/清单/章节）；② 代价要量化（小时数、文档数、数值差），否则读者无法判断严重度；③ 脱敏不彻底就不提交，宁可少写细节。
