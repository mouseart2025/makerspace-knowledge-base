# 公开前安全核查与历史遗留对象处置规程

> **本文档是什么**：把一个 git 仓库从 private 翻转为 public（或首次开源）之前的**强制核查规程**，以及发现「历史重写后托管平台仍留有旧对象」时的**三条处置路径**。它是可执行 SOP，不是经验谈。
> **为什么需要它**：「当前版干净」不等于「历史干净」，「历史干净」也不等于「托管平台对象库干净」。三层里任何一层漏检，翻转可见性的那一刻就会造成**不可撤销**的信息泄漏——爬虫与网页存档通常在分钟级抓走。本库曾在最后一层上栽过：见 [口径事故与返工记录](口径事故与返工记录.md) 的 **A-11**（真实委托方名进入公开历史）与 **A-12**（用 private 态的匿名 404 当作"缓存已清"的有效证据）。
> **脱敏声明**：本文档不出现任何委托方名称、本地绝对路径，也**不出现旧提交的 SHA**。原因见 §七——旧 SHA 本身就是取回脱敏前原文的指针，公开它等于公开泄漏路径。具体 SHA 记录在仓库根的本地未入库清单 `_local_orphan_shas.txt` 中。

---

## 一、什么时候必须走本规程

满足以下任一条，翻转可见性前必须完整走完 §三 的三步核查：

| 触发条件 | 说明 |
|---|---|
| private → public | 包括"临时公开一下再关回来"——公开期间被抓走的内容，关回来也收不回 |
| 首次开源一个既有历史的项目 | 历史里往往混着早期未脱敏的草稿、脚本、路径 |
| 做过历史重写（`git filter-repo` / `filter-branch` / 强推） | 重写只改 refs，**不会**让托管平台上的旧对象消失 |
| 仓库里出现过委托方名、个人隐私、凭据、未公开商务信息 | 即使当前版已改为中性称谓 |

**不需要**走完整三步的情形：仓库自创建起就是 public 且从未写入敏感内容；或仅在 private 之间流转。

## 二、三层洁净模型

核查必须逐层做，且**每层用的工具不同、能证明的事也不同**。把某一层的结论当成另一层的证据，是本规程要防的头号错误。

| 层 | 检查对象 | 工具 | 能证明 | **不能**证明 |
|---|---|---|---|---|
| ① 工作区层 | 当前签出的文件内容 | 词表驱动的全文扫描 | 当前版没有敏感词 | 历史里没有 |
| ② 本地历史层 | 本地全部 refs 可达的提交与 blob | `git log --all -S"<词>"` | 本地历史里没有 | **托管平台对象库里没有** |
| ③ 平台对象层 | 托管平台上**全部**对象，含不可达对象 | 认证态 REST API 按 SHA 直查 | 旧对象是否仍可被取回 | ——（这是最后一层） |

三条常见误判：

1. **用 ① 的结论代替 ②**：当前版改了名字，就以为历史也干净了。历史提交里的原文可通过旧 commit 页与 raw 直链读到。
2. **用 ② 的结论代替 ③**：本地 `git log --all -S` 0 命中，就以为平台侧也没了。`git log --all` 只遍历**本地 refs 可达**的提交；被重写抛弃的旧提交在本地已无 ref（连 `--all` 都看不到），但在平台对象库里仍以**不可达对象**形式存在，且可用 SHA 直接取回。
3. **用 private 态的匿名 404 当作 ③ 的证据**：private 状态下匿名访问**任何东西**都是 404，这个返回值不含任何关于对象是否存活的信息。必须用具备仓库权限的**认证**请求查。详见 A-12。

## 三、公开前三步核查（强制顺序，不可跳步）

### 第 1 步 · 本地层：词表 + 全历史扫描

```bash
# 1a 当前版与"会被发布的文件集"扫描（本库已内置为体检脚本第 8 类检查）
python3 _kbcheck.py --quiet ; echo "exit=$?"      # 0=通过 1=WARN 2=ERROR

# 1b 全历史逐词检索（对词表里每个词都跑一次）
while IFS= read -r w; do
  case "$w" in ''|'#'*) continue;; esac
  printf "%-24s 历史命中提交数=%s\n" "$w" "$(git log --all -S"$w" --oneline | wc -l | tr -d ' ')"
done < _local_secrets.txt

# 1c 工作区命中必须逐个归类：只有"未跟踪且被 .gitignore 排除"才可接受
grep -rIl --exclude-dir=.git -F "<词>" . | while IFS= read -r f; do
  rel="${f#./}"
  t=$(git ls-files --error-unmatch "$rel" >/dev/null 2>&1 && echo 已跟踪 || echo 未跟踪)
  i=$(git check-ignore -q "$rel" && echo 被忽略 || echo 未忽略)
  echo "$rel | $t | $i"
done

# 1d 提交身份一致性（A-14）：作者与提交者双维度去重，必须只有仓库归属账号一种
git log --all --format='%an <%ae>' | sort | uniq -c | sort -rn
git log --all --format='%cn <%ce>' | sort | uniq -c | sort -rn
#   ⚠️ 历史重写后 --all 会把尚未刷新的 refs/remotes/origin/* 旧提交计入；
#      判定请以分支为口径（git log main …），或先 git fetch --prune 再用 --all。
```

**判定标准**：1a 退出码 0；1b 每词 0 命中；1c 的每个命中文件都必须是「未跟踪 **且** 被忽略」；**1d 输出必须只有一种身份，且等于仓库归属账号**。
出现「已跟踪」或「未忽略」的命中 → **停**，先做历史重写，不要进第 2 步。
1d 出现第二种身份 → **停**，先归一：`git commit-tree` 逐个重建受影响提交（保留 tree、提交信息、author/committer 双时间戳）→ `git update-ref refs/heads/<branch> <新SHA> <旧SHA>` 原子替换。**提交元数据也是公开面**——作者名/邮箱会随 `/commit/<sha>.patch` 与 feed 一起发布，改当前版无效（见 [口径事故与返工记录](口径事故与返工记录.md) A-14）。

> 归类这一步不能省。本库的工作区就有 4 个含真实委托方名的本地脚本（脱敏工具、抓取脚本、词表本身），它们**必须**含敏感词才能工作，靠的是「未跟踪 + 被忽略」这个组合来保证不入库。只看命中数会误判成"库里有敏感内容"，只看"库里有敏感内容"又会漏掉一个真的被跟踪的文件。

### 第 2 步 · 平台层：认证态查旧对象可达性

前置：手上要有**历史重写之前**的旧提交 SHA。它们不在本地 refs 里，来源通常是：重写前的备份克隆、`git filter-repo` 生成的 `commit-map`、CI 记录、或事故当时的截图/交接文档。**如果连旧 SHA 都没有，就无法完成本步——此时只能选 §五 的路径 A（删仓重建），因为只有它不依赖你知道旧 SHA。**

```bash
R="<owner>/<repo>"
# 2a 至少查孤儿代的【根 / 中 / 尖】三个提交（只查尖提交会漏掉整代历史）
for s in <OLD_ROOT_SHA> <OLD_MID_SHA> <OLD_TIP_SHA>; do
  printf "%s -> " "$s"
  gh api "repos/$R/commits/$s" --jq '.sha[0:12]+"  date="+.commit.author.date' 2>&1 | head -1
done
# 2b 关键一步：直接取旧提交下的敏感文件内容（commits 返回 200 还不够，要证明 blob 也能取）
gh api "repos/$R/contents/<旧路径>?ref=<OLD_ROOT_SHA>" --jq '{name:.name,size:.size}'
# 2c 顺带确认可见性与 fork 数（fork>0 时任何清理都无效，必须先处理 fork 网络）
gh api "repos/$R" --jq '{private:.private,forks:.forks_count,visibility:.visibility}'
# 2d 复核 gh token 是否具备处置所需 scope
gh auth status
```

**结果判读**：

| 返回 | 含义 | 可否翻转 public |
|---|---|---|
| `404` / `422 No commit found for SHA` | 该对象在平台侧已不可达 | ✅（其余 SHA 也须同样） |
| `200` | **对象仍存活**，公开后即可被任何持 SHA 者读取 | ❌ 必须先走 §五 |
| `403` + 未认证 | 无效证据（private 态必然如此） | ❌ 重做为认证态 |

**孤儿代至少要查根/中/尖三个**，因为一次历史重写可能产生多代孤儿：本库实测就出现过「第一代已被清理（404）、第二代整代 30 个提交全部存活」的情况，而且第二代某个提交的 tree 哈希与现历史某提交完全一致——说明那次重写只改了提交元数据、没改内容，旧 blob 原封不动躺在平台上。只查一个 SHA 就下结论，等于没查。

### 第 3 步 · 翻转可见性，并在翻转后复验

```bash
# 3a 翻转（仅在 1、2 两步全部通过，或 §五 路径已执行完毕后）
gh api -X PATCH "repos/$R" -f private=false
# 3b 翻转后复验：此时"匿名请求"才第一次成为有效证据
curl -s -o /dev/null -w "%{http_code}\n" "https://api.github.com/repos/$R/commits/<OLD_ROOT_SHA>"   # 期望 404/422
curl -s -o /dev/null -w "%{http_code}\n" "https://raw.githubusercontent.com/$R/<OLD_TIP_SHA>/<旧路径>"  # 期望 404
gh api "repos/$R" --jq '{private:.private,forks:.forks_count}'
```

**写结论时必须标注证据获取时的仓库可见性状态**（private / public）。没有这个标注，读者无法判断证据是否有效——A-12 的直接教训。

## 四、为什么平台侧的旧对象不会自动消失

- `git filter-repo` / `filter-branch` + 强推，改变的只是**分支引用指向哪条历史**。被抛弃的提交失去 ref，成为**不可达对象**，但仍留在托管平台的对象库里。
- 托管平台普遍保留通过 commit SHA 直接访问不可达对象的能力（这是设计特性：让既有的链接、issue 引用、CI 记录不至于全部失效）。因此旧 commit 页面、`contents?ref=<旧SHA>`、raw 直链**都可能仍然工作**。
- 除此之外还有一层**缓存视图**（旧 commit 页的渲染缓存、raw 的 CDN 缓存），它独立于对象库，需要平台侧单独清理。
- 本地 `git gc` 对平台侧对象库**没有任何影响**。
- 结论：真正能清除平台侧旧对象的手段只有两类——**删仓重建**（对象库随仓库一起销毁）与**平台工单清理**。**换名公开**属于规避（旧仓继续 private，泄漏路径不对外），不属于清除。

## 五、三条处置路径对比

| 维度 | **A 删仓重建同名** | **B 提交平台 Support 工单** | **C 换名公开** |
|---|---|---|---|
| 做法 | 删除远端仓库 → 用本地干净历史重建同名 public 仓 | 请平台清理不可达对象与缓存视图，确认后再翻转可见性 | 新建另一个名字的 public 仓推干净历史；旧仓永久 private |
| 能否自助 | 可（需 `delete_repo` scope） | 否，须等平台响应 | 可（仅需 `repo` scope） |
| 需要额外权限 | `gh auth refresh -h <host> -s delete_repo` | 无 | 无 |
| 仓库 URL | **不变** | **不变** | **改变**（外部引用/书签需更新） |
| 是否需要预先知道旧 SHA | **不需要**（这是它最大的优势） | 需要（工单里要列出待清理 SHA） | 不需要 |
| 可自证性 | 高：重建后用认证 API 查旧 SHA 应 404 | 中：只能凭平台回复 + 复查 | 高：新仓从未有过旧对象 |
| 耗时 | 分钟级 | 通常数小时至数个工作日 | 分钟级 |
| 残余风险 | 低。需确认：本地克隆完整（`git fsck` 通过、远端=本地）、`forks=0`、无 GitHub Pages/Actions 产物残留 | 低，但依赖平台执行彻底性 | 极低 |
| 主要代价 | **删仓是不可逆动作**，执行前必须确认本地是唯一可信副本且完整 | 等待期不可控；工单沟通成本 | URL 变更；旧仓需长期维护 private 状态 |
| 适用条件 | 有完整本地克隆、无 fork、能拿到删除权限 | 不便删仓（有 fork、有 Pages 域名、有外部依赖 URL） | 急需公开、URL 可变、或不便删仓又不愿等工单 |

**路径 A 命令序列**（确认本地克隆完整后再执行；删仓不可逆）：

```bash
# 0 前置确认：远端 = 本地、fsck 无缺失、forks=0、且本地已 push 全部提交
git status --short ; git log --oneline -1 ; git fsck --no-progress
gh api "repos/<owner>/<repo>" --jq '{forks:.forks_count,private:.private}'
# 1 授权（浏览器一次性完成，会给出 one-time code）
gh auth refresh -h github.com -s delete_repo
# 2 删除远端仓库（只删平台侧副本，本地目录与 .git 完全不受影响）
gh repo delete <owner>/<repo> --yes
# 3 摘掉远端，并清掉本地不可达对象（含刚被替换掉的旧提交），使"新仓不含旧对象"可自证
git remote remove origin
git reflog expire --expire=now --expire-unreachable=now --all && git gc --prune=now
git fsck --unreachable | grep -c 'unreachable commit'          # 期望 0
git cat-file -e <被替换的旧提交SHA> 2>/dev/null && echo "仍在 ❌" || echo "已清除 ✅"
# 4 用本地干净历史重建同名 public 仓（实测：仓名删除后立即可复用，无需等待）
gh repo create <repo> --public --source=. --remote=origin --push
# 5 复验可见性 + created_at（created_at 必须是"刚刚"——这是"确实删掉重建了新仓"的唯一硬证据，
#   只看 private=false 证明不了旧仓没被留着）
gh api "repos/<owner>/<repo>" --jq '{private:.private,forks:.forks_count,created_at:.created_at}'
for s in <OLD_ROOT_SHA> <OLD_MID_SHA> <OLD_TIP_SHA>; do
  gh api "repos/<owner>/<repo>/commits/$s" >/dev/null 2>&1 && echo "$s 仍存活 ❌" || echo "$s 已不可达 ✅"
done
# 6 翻转后必须再用【匿名】请求验一遍（此时匿名证据才有效，见 A-12）
curl -sI "https://api.github.com/repos/<owner>/<repo>/commits/<OLD_SHA>" | head -1
curl -sI "https://raw.githubusercontent.com/<owner>/<repo>/<OLD_SHA>/<旧敏感路径>" | head -1
curl -sI "https://raw.githubusercontent.com/<owner>/<repo>/main/<旧敏感路径>" | head -1
# 7 对齐性复验：远端提交数 / blob 数 / 身份种类 必须与本地一致
#   ⚠️ jq 的键名不能用中文，否则报 "key must be a string"；用 ASCII 键
gh api "repos/<owner>/<repo>/commits?per_page=100" --jq '{n:length,emails:([.[].commit.author.email]|unique),logins:([.[].author.login]|unique)}'
gh api "repos/<owner>/<repo>/git/trees/main?recursive=1" --jq '[.tree[]|select(.type=="blob")]|length'
git ls-remote https://github.com/<owner>/<repo>.git main       # 匿名可达即证明已公开
```

**路径 C 命令序列**：

```bash
gh repo create <新仓名> --public --source=. --remote=public-origin --push
# 旧仓保持 private，在其 README 首行加一条指向新仓的说明
```

## 六、Support 工单模板（路径 B）

提交入口：`https://support.github.com/contact`（选择与仓库/账号相关的类目）。**工单正文可以包含旧 SHA**——它发给平台方，不是公开内容；但**工单截图不得贴进公开仓库或公开 issue**（见 §七）。

**主题**

```
Remove unreachable objects and cached views after history rewrite (git filter-repo)
```

**英文正文**（把 `<...>` 占位符替换为本地清单 `_local_orphan_shas.txt` 中的实际值）

```
Repository: <owner>/<repo>  (currently private)

I rewrote this repository's history with git filter-repo to remove content that
must not be public (a third party's real name and local filesystem paths), then
force-pushed the rewritten history to `main`.

The rewritten history is clean, but the pre-rewrite commits still exist in your
object store as unreachable objects and are retrievable by SHA. Verified today
with an authenticated request against the REST API:

  GET /repos/<owner>/<repo>/commits/<OLD_TIP_SHA>   -> 200
  GET /repos/<owner>/<repo>/commits/<OLD_ROOT_SHA>  -> 200
  GET /repos/<owner>/<repo>/contents/<OLD_PATH>?ref=<OLD_ROOT_SHA> -> 200, <SIZE> bytes

That last response returns the pre-rewrite version of the file, i.e. the content
I removed is still readable. The orphaned generation contains <N> commits; its
root is <OLD_ROOT_SHA> and its tip is <OLD_TIP_SHA>. Full list of old SHAs:
<OLD_SHA_1>, <OLD_SHA_2>, ... (available on request).

The repository has 0 forks, so no fork network needs to be detached.

Please remove these unreachable objects and any associated cached views / raw
URL caches so that the old SHAs return 404. I intend to make the repository
public once you confirm the removal, and will re-verify by SHA afterwards.

Thank you.
```

**中文摘要（内部留档用）**：说明仓库名、已做 filter-repo 重写、旧提交仍可按 SHA 取回（附三条 API 实测返回码）、孤儿代提交数与根/尖 SHA、forks=0、请求清理不可达对象与缓存视图、清理完成后才翻转 public 并复验。

## 七、旧 SHA 本身也是敏感信息

这一条反直觉，但很重要：**指向脱敏前原文的 commit SHA，等价于原文本身**。

- 泄漏路径极简：`https://<host>/<owner>/<repo>/commit/<SHA>` 或 `.../contents/<路径>?ref=<SHA>`，无需任何权限（仓库公开时）。
- 因此旧 SHA 不得出现在：公开仓库的任何文件、公开 issue / PR / discussion、公开博客或截图、对外交付物、以及**本规程文档自身**。
- 存放约定：写在仓库根的 `_local_orphan_shas.txt`（已被 `.gitignore` 的 `_local_*` 规则排除，**绝不入库**），内容包含：每个旧 SHA、其代际位置（根/中/尖）、核查日期、当时的可见性状态、API 返回码、取回到的文件大小。这份清单同时是 §三 第 2 步的输入和 §六 工单的取值来源。
- 工单、内部报告里引用时，公开载体一律写作「旧根提交」「孤儿代尖提交」等**位置描述**，不写哈希。

## 八、执行记录

### 2026-09-14 · 某科普场馆项目知识库「恢复 public」请求

| 项 | 结果 |
|---|---|
| 触发 | 委托方要求把已转 private 的知识库仓恢复 public |
| 证据获取时的可见性状态 | **private**（本行按 A-12 ③ 强制标注） |
| 第 1 步 · 工作区层 | 体检脚本退出码 0（0 ERROR / 0 WARN） |
| 第 1 步 · 本地历史层 | 词表 4 词，`git log --all -S` **全部 0 命中** |
