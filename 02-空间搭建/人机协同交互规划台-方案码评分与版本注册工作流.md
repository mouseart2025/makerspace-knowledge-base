# 人机协同交互规划台工作流：方案码 · 实时评分 · 版本注册

> 定位：本工作流是布局规划方法链（SLP 判断层 → 实测校核层 → 落位数据链）的**最后一环——协同编辑层**。此前各环节产出的是"静态结论"（图纸 + 文档），甲乙方对结论的任何调整都要靠"文字描述 → 规划师改图 → 再发图"往返，一轮以天计。规划台把"改方案"变成甲方自己拖一拖、点一下的事，把"定稿"变成一个可评分、可注册、可回溯的版本对象。
> 一句话：**图纸是只读的，规划台是可写的；方案码是图纸的"源代码"，评分是方案的"体检报告"，注册表是版本的"户口本"。**
> 实战验证：该项目 `规划云图-v2.html`（单文件，零依赖），甲方教师在没有技术指导的情况下独立完成了两版方案（v6.1 = 91.7 分 / v7 = 74.7 分定稿）并通过方案码回传入档。

---

## 〇、什么时候需要这一层

出现以下任一信号，静态图纸就不够用了：

1. 甲方开始说"我觉得这里应该……"但描述不清位置——**他有空间直觉，没有表达工具**；
2. 方案在"授课态 / 活动态"等多态之间切换，一张图根本画不下；
3.  revision 超过 3 轮，"哪版是准的"开始靠记忆；
4. 甲乙双方要"共同创作"而非"乙方提案、甲方审批"。

反面：如果方案已基本冻结、只剩施工深化，规划台是过度工程——直接用 CAD/图纸。

## 一、五件套架构

```
① 单文件 HTML 规划台（零依赖，双击即开，微信可发）
② P1 方案码（幂等文本交换格式）
③ 实时评分引擎（基线 = 100 自校准）
④ REGISTRY 版本注册表（署名入档，全员可见）
⑤ 总览首页（全区一图 + 成果索引）
```

### ① 规划台：最小交互集

| 交互 | 说明 | 为什么必需 |
|---|---|---|
| 拖拽移动 | 50mm 吸附栅格 | 核心动作 |
| Shift+点选多选 | 多件一起拖 | 成排桌椅调整是高频操作 |
| 旋转 90° | 绕中心旋转后吸附 | 朝向敏感的台架必须可转 |
| 暂存区（挪出/放回） | 不进评分但保留在方案里 | "这个先不放"是真实决策 |
| 1m 尺寸网格开关 | 带标尺标签 | 非专业用户估尺寸的唯一依靠 |
| 三色归属 | 甲方清单 / 规格书 / 我方建议 | 采购责任一目了然，防止"偷偷加设备" |
| 点选显示名称 + 去重清单 | 清单与图双向定位 | 核对件数 |

**踩过的坑**：
- 旋转后编号丢失 → 标签绘制要以**旋转后的外接矩形**重新定位，窄条（宽 <30px）改竖排文字；
- 上下边缘文字被裁 → SVG viewBox 四周要留 300–500mm 余量，标尺标签放墙外侧；
- 多选与拖拽手势冲突 → Shift 按下时不起拖，click 事件里处理多选切换；
- `alert/confirm` 会卡死无头浏览器测试 → 验证脚本里先打桩。

### ② P1 方案码：把布局变成可粘贴的文本

格式：`P1:<编号>.<实例号>.<x>.<y>.<rot>[.s];...`（`.s` = 暂存）

设计纪律：
- **幂等**：同一个码恢复两次 = 恢复一次；解码器按"编号+实例号"寻址，不依赖顺序；
- **可增补**：码里出现新实例号时按原型克隆（甲方在旧版页面上加的件，码发到新版页面不丢）；
- **跨区自识别**：码里含 `C-/D-` 前缀即判为 CD 区方案，粘贴后自动跳区恢复；
- **文本即交付**：能走微信、邮件、issue，不依赖任何服务端——这是它能被甲方接受的根本原因。

### ③ 实时评分：让"好不好"即时可见

```
总分 = 35×落位率（暂存不计）+ 30×碰撞/越界（每处 −15%）
     + 15×foot 净距（超基线每处 −25%）+ 20×焦点容量达成
```

关键设计——**基线 = 100 自校准**：页面加载时先对"系统基线布局"实测一次 foot 重叠数，作为及格线；方案只有**比基线更挤才扣分**。否则基线本身拿不到满分，用户会对分数失去信任（"系统自己都摆不好凭什么扣我"）。

评分面板必须**同步给出人话解释**（优势 / 劣势 / 提示三栏），只给一个数字会被无视。体检结论要诚实：定稿方案 74.7 分照样入档，但三处扣分项（越界、互叠、偏密）写进注册表备注，甲方负责人知悉签字——**分数是决策材料，不是验收门槛**。

### ④ REGISTRY 注册表：版本治理的最小实现

- **本机草稿**：localStorage（`bb2_versions_<区>`），只有保存者自己可见，可删；
- **入档正式版**：方案码发给 AI/规划师 → 评分复核 → 把 `{名称, 署名, 分数, 时间, 备注, 码}` 写进单文件内的 `REGISTRY` 数组 → git 提交 → 全员可见，不可删；
- **默认方案**：`default: true` 标记，新访客打开即见定稿；历史下拉可随时切回基线或任何入档版。

纪律：**删除入口只对"当前画布正在显示的本机草稿"开放**，不做下拉选删——用户分不清下拉里哪条是哪条，误删率极高（实战踩过）。

### ⑤ 总览首页：规划的"仪表盘"

- 全区（L 型 ABC/D/EF）一图总览，每区渲染其**当前方案**（优先级：本机编辑中 ＞ 入档默认 ＞ 系统基线）；
- 点击分区进入对应规划台；
- 下方挂**成果索引**：把项目所有现行交付物（设计文档、图纸、清单、分析工具、依据）按组链接，全部指向权威版本索引登记的现行版——首页同时是项目的"文档门户"。

## 二、与 SLP 方法链的衔接

| 层 | 回答的问题 | 工具 |
|---|---|---|
| 判断层 | 谁该挨着谁、先做哪个区 | REL 关系图 / 打分表 / 力度评级（见 [SLP系统布置设计-专题补充.md](SLP系统布置设计-专题补充.md)） |
| 校核层 | 判断经得起实测吗 | 分离度 / 绕行系数 / 集中分散因子探针 |
| 落位层 | 具体坐标是什么 | 落位器 + 双包络规则 |
| **协同层（本篇）** | **人怎么参与改与定** | **规划台五件套** |

协同层的评分项不是拍脑袋：碰撞/越界对应 SLP 的红线与构件约束，foot 净距对应操作净空与通道红线，焦点容量对应需求条目（如 40 座）——**评分公式是方法链结论的可执行化**。

## 三、适用边界与反模式

1. **不要**把规划台做成 CAD：它只回答"哪个件放哪、朝哪、放不放"，不回答构造与施工（呼应项目铁律：交付物不得越界到施工方案）；
2. **不要**给评分加太多因子：4 个以内，每个都能向非专业用户一句话讲清；
3. **不要**让服务端成为必需品：协同规划的场景常常就是"甲方在微信那头等一张图"，单文件 + 方案码是下沉能力最强的形态；
4. 暂存区是**决策的一部分**（"这个不买/缓买"），不是垃圾桶——入档时暂存件数写入备注。

## 四、检查清单

- [ ] 基线布局自测 = 100 分（校准成立）
- [ ] 方案码往返：编码 → 解码 → 再编码，逐字一致（幂等）
- [ ] 新访客打开 = 默认方案；历史下拉含基线 + 全部入档版
- [ ] 删除按钮只在画布显示本机草稿时可用
- [ ] 无头浏览器渲染回归：总览 / 每区规划台各一张截图
- [ ] 注册表备注写明该版的**已知折中**（扣分项是什么、谁接受的）
