# 项目目录治理：版本迭代下的整理与归档工作流

> 配套文档：版本纪律的**原则层**（"现有文件不覆盖、修订另起版本号"）见 [AI空间方案工作流-九阶段端到端方法论.md](AI空间方案工作流-九阶段端到端方法论.md) 的「版本即资产」与 S1/S9 红线；本文解决的是**执行几个月后目录必然膨胀，怎么收拾**这件事。项目文档命名与版本脱节的常见事故，见 [口径事故与返工记录.md](../00-知识库治理/口径事故与返工记录.md)。

## 〇、结论先行

**大多数"目录太乱"不是文件放错位置，而是旧版本没有退出通道。**

一次实测（某已建空间改造项目，持续迭代 4 个月）：

| 指标 | 整理前 | 整理后 | 降幅 |
|------|--------|--------|------|
| 顶层条目数 | 90 | **42** | −53% |
| 建模支线目录（文件数 / 体积） | 8418 个 / 343 MB | **75 个 / 25 MB** | −99% / −93% |
| 3D 资产目录顶层条目 | 166 | **66** | −60% |
| 版本控制未跟踪项 | 28 | **14（其中二进制 0 个）** | −50% |

**共移动约 240 项，删除 0 项。**

三条不可动摇的原则：

1. **不搬家，只分离** —— 被大量相对路径引用的目录**原位不动**；旧版本进 `_归档/`。
2. **只移动，不删除** —— 归档是"改存放位置"，不是"销毁"。
3. **用导航替代搬迁** —— 写清"哪一版为准"（索引）与"各目录装什么"（地图），比把文件挪整齐更有效，且零断链成本。

## 一、动手前必答的三个问题

整理失败的典型原因是**先动手再思考**——把被引用的目录搬走，导致上百处相对链接集体失效。所以先答三问：

| 问题 | 为什么问 | 实测答案（示例） |
|------|----------|------------------|
| 哪些目录被**大量相对路径引用**？ | 搬它们 = 大面积断链 | 模型目录、素材背景目录、三维重建目录、勘察资料目录（合计 100+ 处引用） |
| 哪些是**现行**、哪些**已被取代**？ | 决定谁进 `_归档/` | 版本号最高且语义最新 = 现行 |
| 哪些是**临时产物**（过程性文件）？ | 这类最该归档，且几乎零引用 | 诊断脚本 `_diag*.py`、探测脚本 `_probe*.py`、备份文件 `*.blend1`、中间渲染图 |

> ⚠️ **先统计，再动手。** 对每个候选搬迁目录，先统计它被多少个文件以相对路径引用。**命中一次就说明它不能搬。** 这一步用查询即可完成，不要凭印象——"我感觉这个没人用"是本工作流最常见的事故来源。

## 二、三类判定：唯一的分拣标准

| 类别 | 判定依据 | 处理 | 版本纪律 |
|------|----------|------|----------|
| **现行** | 版本号最高 + 语义最新 + 有下游引用 | **原位不动** | 不动 |
| **已被取代** | 同族存在更新版本 | 进 `_归档/<族名>-旧版/` | **加归档横幅**，逐跳串联 |
| **临时产物** | 一次性诊断/探测脚本、中间截图、备份 | 进 `_归档/05-临时脚本与过程产物/` 等 | 不加横幅（无版本语义） |

### 2.1 归档横幅：让旧文件自己指路

在旧文件**头部**加一段引用块，标明现行版本与归档原因：

```markdown
> 📁 **本版已归档（保留不修改）。现行版本：`<新文件名>`。**
> 归档原因：<一句话，写清是什么替代了它>。
```

### 2.2 逐跳串联，不要全部指向最新版

**反例**：v1、v2、v3 的横幅都写"现行版本：v4"。
**正例**：v1 指向 v2，v2 指向 v3，v3 指向 v4。

理由：逐跳串联保留了完整的演进路径，半年后回溯"某一版当时为什么这么定"仍可顺着链条走下去；全部指向最新版则丢掉了中间态。

> **推论**：归档时**不必回头修改更早的横幅**——老横幅指向它当时的下一版，仍然正确。这条让整理工作量从 O(n) 降到 O(新增)。

## 三、归档区设计：按"族名 + 为什么归档"分，不按时间分

```
_归档/
├── README-归档说明.md                    ← 必写，见 §四
├── 01-<方案族>（已作废·<一句话原因>）/    ← 整族作废，原因要显式
├── 02-<现行方案>-旧版/                    ← 现行方案的旧版本族
├── 03-<专项报告>-旧版/                    ← 单篇报告的多版本
├── 04-过程稿与已移除方向/                 ← 中途废弃的路线
├── 05-临时脚本与过程产物/                 ← 无版本语义的临时件
├── 06-旧版模型与渲染/                     ← 二进制大件（不入版本控制）
├── 07-<项目特化>过程产物/                 ← 相机标定帧、旧版图纸等
└── 08-索引旧版/                           ← 索引类文档的旧版
```

**命名铁律**：目录名要包含「**为什么归档**」，不能只有版本号。

| 差 | 好 |
|---|---|
| `01-旧方案` | `01-布局方案1-3（已作废·需求专业口径由 4 改 3）` |
| `0930/` | `02-设计方案-旧版` |

时间可以进名字当后缀，但**不能是唯一信息**——半年后没人记得 0930 那天改了什么。

## 四、导航替代搬家（本工作流的核心手法）

**不搬目录，改在入口处写导航。** 三份文档替代物理重组：

| 文档 | 位置 | 回答什么问题 | 必备内容 |
|------|------|--------------|----------|
| **README 文档地图** | 项目顶层 | "我要干 X，该看哪份？" | 权威入口表（按用途索引）+ **交付边界专章** + 仓库结构 + 版本卫生规则 |
| **权威版本索引** | 项目顶层 | "哪一版为准？旧版去哪了？" | 现行交付物 ↔ 依据 ↔ 版本增量；归档区地图；待定夺项；版本卫生规范 |
| **归档说明** | `_归档/` 内 | "这里装的是啥？怎么取回？" | 见下 |

### 4.1 归档说明必含四条

1. **导航表**：归档目录 → 收什么 → 现行版本是谁
2. **路径声明**：`旧文档内的相对路径引用未改，请按归档后位置解析`
3. **不入库声明**：`归档区二进制（png/blend/glb）不进版本控制，需要时从本地归档取`
4. **恢复方法**：**建议 `cp` 不建议 `mv`** —— 从归档取回时保留归档副本，避免二次断链

### 4.2 为什么坚持"不搬家"

物理搬迁的隐性成本被严重低估：

| 成本 | 说明 |
|------|------|
| 断链面 | 100+ 处相对路径引用需逐个改写，漏一处就是静默失效 |
| 工具假设 | 脚本、校验器、hook 里写死的路径假设可能全部失效（例：基线校验脚本依赖特定子目录与只读副本） |
| 历史文档 | 已归档的旧文档内部引用**不应改写**，搬迁会让它们指向不存在的路径 |
| 复算能力 | 复现脚本一旦断链，"数字可复现"这条规范就落空了 |

而**写导航的成本是固定的三份文档**，且不破坏任何既有引用。因此：

> **默认策略 = 分离（旧版本入归档）+ 导航（三份文档）。物理重组顶层目录是可选项，须先问清是否接受断链代价，不要顺手做。**

## 五、执行脚本：两个模板

**统一约定**：默认**干跑**（只打印不改动），`--apply` 才真执行；一律用"移动"操作，**绝不删除**。

### 5.1 模板 A：通用分拣（计划字典驱动）

适合"根目录一堆文件要按族归档"。声明一份 `{归档子目录: [源路径...]}` 计划表，逐个搬。

**关键设计点**：

- **幂等**：`源不存在` 与 `目标已存在` **都跳过** —— 脚本可重复运行不报错、不覆盖
- **目录整体搬时保持原目录名**（区分"搬目录"与"搬文件"两个分支）
- **支持前缀/通配批量**（如 `_gen_v*.png`）匹配同族过程产物
- **报告按归档子目录分组打印**，便于人工核对后再执行

### 5.2 模板 B：白名单保留法

适合"某个目录里只有少数几个是现行的"。**反过来写：列保留集，其余全部归档。**

```python
KEEP_MODEL = {"<基线模型>.skp", "<冻结基线模型>.skp", ...}   # 白名单
KEEP_DATA  = {"<坐标数据源>.json", ...}
KEEP_DIRS  = {"工具脚本目录", "自动摆放脚本", "基线归档"}
KEEP_FILES = {"<生成脚本>.rb", ...}
```

**附加技巧**：对批量渲染图按**版本号正则**筛，只归档低于当前基线的：

```python
m = re.match(r"基础模型_v(\d+)_(顶视图|鸟瞰图)\.png$", name)
keep = not (m and int(m.group(1)) < 13)      # v13 起保留，v3–v12 归档
```

> 🐛 **踩过的坑（务必避免）**：白名单判断的三元组下标方向写反——
> `(moved, kept)[name in KEEP_DIRS]` 是**对的**（`True` → 索引 1 → kept）；
> 若误写成 `[name not in KEEP_DIRS]`，会把保留项移走、其余留下，**恰好反了**。
> **所以必须先干跑**：干跑一次就能发现，直接执行则要收拾残局。

## 六、版本控制策略：归档区二进制排除

归档区通常塞进 GB 级过程产物（渲染帧、模型文件、导出资产）。原则：**只入库文本与脚本**。

```gitignore
# ---- 归档区：只留文本与脚本，大体积/可再生二进制不入库 ----
_归档/**/*.png
_归档/**/*.jpg
_归档/**/*.blend
_归档/**/*.glb

# ---- 例外：已被作废报告实际引用的插图本体 ----
!_归档/**/方案1_插图/**/*.png
```

### 6.1 规则顺序铁律

`!例外` **必须后置**（写在该模式族的忽略规则之后）。版本控制按后匹配者胜出，顺序错了例外就不生效。

### 6.2 验证要跑两条

```bash
# ① 确认某文件被排除（输出行首无 ! 即表示被忽略）
git check-ignore -v "_归档/05-临时脚本与过程产物/_gen_v3_top.png"
# → .gitignore:79:_归档/**/*.png

# ② 确认例外生效：该 png 应被跟踪，故不应出现在未跟踪计数里
git status --porcelain | grep '^??' | grep -ci png
# → 0
```

> ⚠️ **误报取证法**：`git check-ignore -v` 对**已被跟踪**的文件也会输出规则行，但行首带 `!` 前缀（表示"反向排除"）。
> 看到 `!_归档/**/方案1_插图/**/*.png` 不要惊慌——那说明它**正被跟踪**，恰好是想要的结果。用第 ② 条的未跟踪计数交叉验证即可。

## 七、整理后必跑的五道回归

整理动了大量文件，"看起来没问题"不等于没问题。以下是可机械验证的五道关卡：

| # | 检查 | 判据 |
|---|------|------|
| R1 | **项目自带的基线/一致性校验** | 跑项目自身的校验脚本，须输出通过（例：模型基线校验须报"完好"） |
| R2 | **版本控制变更成对** | `git status --porcelain`：每个移动应同时出现旧路径删除 + 新路径新增；若某文件只有删除没有新增，说明它被移进了忽略区，需确认是否符合预期 |
| R3 | **导航文档相对链接 0 失效** | 抽出所有 markdown 内链逐个判存在 |
| R4 | **表格与编码完整性** | 表格列数一致；替换字符（U+FFFD）计数为 0 |
| R5 | **全量孤儿检查** | 对每个"已删除"路径，确认能在归档区找到同名文件 |

### 7.1 R5 是最硬的证据（推荐固化为脚本）

```bash
git status --porcelain | grep -E '^( D|D )' | cut -c4- | while read f; do
  find _归档 -name "$(basename "$f")" -print -quit 2>/dev/null | grep -q . \
    || echo "⚠️ 未找到: $f"
done
```

实测输出：**受检 200 项 / 未在归档区找到 0 项**。这条把"零丢失"从口头承诺变成可复现的事实。

> **为什么 R2 要专门看**：移动操作若被版本控制识别为成对变更，历史可追溯；若某文件只有删除记录，它的内容就退出了版本控制视野——对**文本文件**这通常意味着策略失误。

## 八、顶层条目数的健康区间

整理前先数顶层条目。经验值（单项目仓库）：

| 项目规模 | 健康顶层条目数 |
|----------|----------------|
| 单方案文档型 | 20–30 |
| 多方案 + 建模 + 勘察 + 设备型 | **40–50** |

超过上界就该考虑两步走：**第一步（必做）**分离旧版本；**第二步（可选）**顶层物理分组（如 `01-需求/ 02-勘察/ 03-设计/ 04-方法/`）。

> 第二步会断掉更多相对路径，**代价高于第一步**，所以它是可选项而非必做项。

## 九、标准流程（12 步）

1. 记录基线：数顶层条目数，记录关键目录的文件数与体积
2. 统计引用：圈出**不可搬**目录清单（命中一次即不可搬）
3. 三类标注：给每个候选文件标"现行 / 已被取代 / 临时产物"
4. 设计归档区子目录名（**含"为什么归档"**）
5. 写整理脚本（模板 A 或 B），**干跑**
6. 人工核对干跑报告 → 无误再执行
7. 给归档的文档族**加归档横幅**（逐跳串联）
8. 更新版本控制忽略规则（归档二进制排除 + 例外后置）
9. 写/重写 **README 文档地图**
10. 写**权威版本索引** + **`_归档/README-归档说明`**
11. 修正**仍现行**文档里指向旧位置的路径（归档文档内部的引用**不改**）
12. 跑 §七 五道回归

## 十、反例清单（做错的样子）

| 反例 | 为什么错 | 正解 |
|------|----------|------|
| 把被 100+ 处引用的目录搬进 `_归档/` | 大面积断链，且要改上百处引用 | 原位不动，只归档其中的**旧版本文件** |
| 直接删除旧版本 | 不可逆，且历史追溯丢失 | 一律移动进 `_归档/` |
| 归档的二进制也提交入库 | 仓库膨胀到 GB 级 | 归档区二进制排除 |
| 所有旧版横幅都写"现行版本：最新" | 丢掉中间版本链 | **逐跳串联** |
| 归档目录按时间命名（`0930/`） | 半年后没人知道里面是什么 | 按**族名 + 原因**命名 |
| `!例外` 写在忽略规则之前 | 顺序错，例外失效 | `!` 规则**后置** |
| 只写 README 不写索引 | "哪版为准"靠记忆 | README + **权威版本索引** 双文档 |
| 顺手做顶层物理分组 | 超出授权，断更多链接 | **先问**再动 |
| 脚本不干跑直接执行 | 白名单判断写反会移走保留项 | **必须干跑** |

## 十一、与「版本纪律」的分工

两条线不是替代关系，而是**原则层与操作层**：

| | 原则层（版本纪律） | 操作层（目录治理，本文） |
|---|---|---|
| 回答 | 改动时**该不该新建版本号**？ | 攒了 N 个月后**怎么收拾**？ |
| 典型条目 | 现有文件不覆盖；另起版本号；交付稿清洗内部版本号；数据源改动 = 结论改动 | 三类分拣；归档区设计；导航替代搬家；忽略规则；五道回归 |
| 触发时机 | 每次改动 | 目录膨胀到影响检索时（顶层条目超健康区间） |
| 关系 | 前者执行得越严格，后者的**素材越多**（这是好事：可追溯的历史全在） | 后者的归档结构反过来让前者更好执行（旧版有明确去处） |

> **一句话**：版本纪律让历史**可追溯**，目录治理让历史**不碍事**。缺前者，整理时无从判断哪版为准；缺后者，几年后目录会大到自己都不敢动。
